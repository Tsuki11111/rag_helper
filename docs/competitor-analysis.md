# 竞品分析：买小购 vs 京东言犀 AI 客服

> 版本：v1.0（2026-11-24）
> 分析对象：**京东言犀**（京东云智能客服 / 言犀小智 / 言犀智能体平台）
> 我方产品：**买小购**（一次买够平台客服智能体，仓库 `rag_helper`）
> 资料口径：公开官网/京东云产品页、第三方评测与行业文章；**未对言犀做实际采购和场景压测**。
> 因此本文把“厂商公开宣称”和“可验证事实”分开写；涉及价格、解决率、客户数的数字均标注为公开口径，采购前需试用复核。

---

## 0. 结论先行

1. **言犀不是“一个 RAG 问答机器人”，而是京东云的全链路客服/营销平台**：渠道、语音、数字人、质检、坐席辅助、知识库、智能体编排、私有化交付都在一张产品矩阵里。它的核心优势是京东零售交易数据、物流/售后链路和规模化运营经验，不是单点模型能力。
2. **买小购与言犀不是同一物种**：言犀卖“企业客服基础设施”，买小购做“自建电商平台内的客服智能体”。买小购的优势在**与 ItsMyGo 交易链路的深度耦合、工具权限与确认闭环、数据主权、成本与可定制**；短板在**知识运营、渠道覆盖、品牌、规模化验证**。
3. **竞争策略：不在“全渠道/全场景/大模型参数”上正面竞争**。买小购应定位为“**可私有化、可审计、和订单/售后深度打通的平台型客服智能体**”，用深度场景 + 数据不出域 + 低成本交付，去吃言犀覆盖不到或不愿意服务的中型自建平台。

**一句话定位**：

> 言犀是“京东生态的客服操作系统”；买小购是“自建电商平台的客服智能体中枢”——不追求什么渠道都接，追求产品文档、订单、售后政策三类问题答得准、查得到、办得对、可追溯。

## 1. 分析目的与边界

### 1.1 目的

- 判断买小购与言犀的**真实竞争关系**：替代、互补，还是不同客群；
- 给出产品定位、销售话术和 roadmap 建议；
- 面试/答辩时能讲清楚“为什么已有言犀，还要自建”。

### 1.2 边界

- **只分析京东言犀**；店小蜜、七鱼、智齿、Intercom Fin 等仅在必要时作为参照，不展开。
- 言犀产品线很宽（客服、外呼、数字人、营销、质检、CRM），本文只聚焦**与买小购重叠的“在线客服智能体 + 知识库 + 交易工具”**。
- 所有“言犀能力”均来自公开资料；**没有拿到言犀的测试账号，也没有做同题对比**。文中用“公开宣称/第三方评测/待验证”区分置信度。

### 1.3 评价原则

- 同一场景、同一口径比较，不用“我方实测 vs 对方官网宣传”直接下结论；
- 功能有无只是入场券，重点看**做到什么程度、失败怎么兜底、数据在哪里、多少钱**；
- 不把“大厂”当不可战胜，也不把“自建”当天然更安全。

## 2. 竞品概况：京东言犀

### 2.1 产品定位

言犀是京东云面向企业级市场的智能人机交互平台，以**言犀大模型**为底座，融合京东多年的客服、营销和供应链实践。公开资料将其描述为“模型训练 + 知识管理 + 智能体编排 + 应用发布 + 运维监控”的全链路 AI 生产平台，而不是单一客服机器人。

### 2.2 产品矩阵（与买小购相关的部分）

| 能力 | 言犀公开能力 | 与买小购的关系 |
|---|---|---|
| 在线客服 | 多轮对话、意图识别、情感识别、人机协作 | 直接重叠 |
| 语音/外呼 | 智能语音应答、语音外呼、数字人 | 买小购不做 |
| 知识库/RAG | 智能知识库、Advance RAG、商品/订单/售后规则 | 直接重叠 |
| 智能体平台 | 可视化编排、工作流、插件/工具、多模型接入 | 部分重叠（我方是代码级编排） |
| 交易执行 | 京东订单/物流/售后、京麦审批、自动执行 | 直接重叠（但生态不同） |
| 运营工具 | 智能质检、坐席辅助、培训、数据分析 | 买小购只有评测/缺口，弱 |
| 交付 | SaaS、VPC、私有化、等保/ISO 认证（公开宣称） | 买小购可私有化，但无认证背书 |

### 2.3 目标客户与商业模式

- **目标客户**：中大型品牌、京东生态商家、零售/金融/政务等对客服规模和合规有要求的企业；公开资料称已服务超过十万家企业客户。
- **收费**：公开资料显示为“免费额度 + 订阅/按量 + 企业定制”的混合模式；私有化、专属算力、SLA 属于企业定制，价格通常从数十万元起，具体需商务报价。**官网未完全公开标准价，本文不写死具体金额。**
- **交付**：SaaS 开箱即用；企业版支持 VPC/私有化、专属算力、定制模型、SLA。公开资料提到等保三级、ISO 27001。
- **锁定点**：京东生态（订单/物流/售后/京麦）、京东云、言犀模型；跨平台和非京东自建系统的适配相对弱。

### 2.4 言犀的核心优势（公开口径）

1. **零售 Know-how 深**：商品参数、订单状态、物流、价保、售后规则都在京东交易链路里，回答不是通用模型的“标准话术”。
2. **全链路覆盖**：从售前导购、售中咨询到售后工单、外呼、质检、坐席辅助，一个供应商全包。
3. **规模化验证**：公开宣称智能客服处理 80% 以上售后咨询、解决率超过 92%，落地 1000+ 业务场景；这些数字未经我方复核，但代表其运营成熟度。
4. **企业级交付**：私有化/VPC、等保/ISO、SLA、实施与运营服务，适合大客户采购流程。
5. **模型与生态**：言犀大模型 + DeepSeek 双模型、多模型接入；与京东云 PaaS、京麦、商家后台协同。

### 2.5 言犀的约束与弱点（公开资料/第三方评测）

1. **生态绑定**：强在京东，跨淘宝/拼多多/抖音或自建商城时，订单/售后/物流的深度会下降；公开资料也提到跨平台能力较弱。
2. **知识库依赖**：AI 客服不是开箱即用，知识库不维护就会答非所问；知识结构、转人工阈值需要运营。
3. **个性化/情绪争议弱**：规则明确的重复问题强，复杂争议、强情绪仍需人工；第三方反馈有“机械回复、转人工难、缺人味”的抱怨。
4. **企业级门槛高**：中大型品牌更合适；中小企业面临部署成本、定制周期、学习成本。公开资料也提到小店铺更适合轻量产品。
5. **效果指标可能反噬**：有商家反馈 AI 客服省人力但差评率/转化率变差；说明“自动化率”不能替代“服务体验”。
6. **定价不透明**：公开标准价有限，采购需要商务流程；对预算敏感的中小客户不友好。

> **对我们的含义**：言犀的弱点不是“技术差”，而是“**标准化产品 + 生态绑定 + 企业级交付**”带来的覆盖盲区。买小购的机会在盲区里，而不是在它的主战场。

## 3. 我方概况：买小购

### 3.1 定位

买小购是一次买够平台的客服智能体：**产品使用文档问答 + 商品导购 + 订单/物流查询 + 下单/退款/催办草稿 + 平台政策/话术**，通过 gRPC 接入 ItsMyGo Java 平台，界面全部在平台侧。

### 3.2 与言犀的结构差异

| 维度 | 京东言犀 | 买小购 |
|---|---|---|
| 产品形态 | 企业级客服/营销 SaaS + 智能体平台 | 平台内客服智能体（代码级交付） |
| 交易链路 | 京东订单/物流/售后/京麦 | ItsMyGo 自有订单/库存/支付/售后 |
| 知识库 | 智能知识库 + Advance RAG | 产品手册 8 节点导入 + 五路召回 + rerank/gate + 终稿接地 |
| 工具执行 | 插件/工作流/京麦审批 | 9 个订单工具 + 表单 + prepare/confirm + 工具票据 |
| 渠道 | 网页/APP/小程序/企微/钉钉/飞书/电话/数字人 | 平台内聊天（gRPC/SSE/HTTP 调试） |
| 部署 | SaaS/VPC/私有化 | 自有 Docker/VM，可私有化 |
| 运营 | 质检/坐席辅助/培训/分析 | 评测/judge、query_runs、知识缺口、话术库 |
| 规模 | 十万级企业客户（公开口径） | 单平台、单实例，尚未规模化 |
| 成本 | 企业订阅/定制/实施 | 基础设施 + 模型 token，单轮约 1–2 分钱（本地实测口径） |

### 3.3 我方真实优势

1. **交易链路深度**：不是“查订单”这么简单，而是工具票据绑定用户/会话、写操作只 prepare、用户确认后 Java 重新校验执行；模型不直接写业务库。
2. **数据主权**：Mongo/Redis/Milvus/MinIO/模型 key 都在自己环境；对“数据不出域”的客户，比 SaaS 更容易讲清楚。
3. **可定制**：代码级可控，产品文档切分、检索权重、政策库、话术、表单字段都能按平台改；言犀是配置级/平台级定制。
4. **RAG 可追溯**：稳定 `chunk_key`、五路召回、rerank 分数、query_runs、终稿接地、知识缺口闭环；出问题能定位到切片和调用。
5. **成本结构**：没有企业 license 和实施费；适合预算有限、但愿意自己运维的中型平台。
6. **评测意识**：151 条 pytest + 49 条 regression + LLM-as-Judge；这在自建项目里是差异化，不是“测试多”。

### 3.4 我方短板（必须诚实）

- 单实例、无多租户隔离、无 K8s/Prometheus/OTel、无多活；
- 只有平台内渠道，没有电话/企微/抖音/数字人；
- 知识运营工具弱：上传/版本/回滚/质量评估还没有产品化；
- 没有人工坐席工作台、质检、培训、CRM；
- 模型依赖外部 API，没有自训模型；
- 品牌、客户数、规模化验证几乎为零。

## 5. 场景走查

> 说明：言犀部分依据公开能力描述推断，**未实测**；买小购部分来自本项目真实链路与冒烟结果。

### 场景 A：产品说明书问答（如 HAK180 烫金膜盒安装）

- **言犀**：智能知识库 + RAG + 商品参数，理论上可上传手册并配置问答；优势是知识库运营工具、全渠道触达、大模型能力。风险是长文档/图片步骤/型号差异需要人工运营，公开反馈也提到“知识库不维护就答非所问”。
- **买小购**：8 节点导入、稳定 `chunk_key`、五路召回（向量/HyDE/BM25/KG/联网）、rerank、终稿接地、配图引用；真实冒烟能答出全幅/半幅两种安装步骤。风险是知识运营仍靠脚本，评测集小。
- **判定**：在“单产品手册深问答”上，买小购可以做到不输通用客服；言犀赢在规模化运营和渠道，而不是单题深度。

### 场景 B：查订单 / 退款草稿

- **言犀**：京东订单/物流/售后/京麦审批深度耦合，公开宣称可自动执行退差价、改地址、催发货；在京东生态内优势明显。
- **买小购**：gRPC 票据绑定 `userId/sessionId`，工具回调 Java 内部接口；写操作只生成 `PENDING_CONFIRM` 草稿，用户确认后 Java 重新校验库存/地址/状态；不暴露 PII。非 ItsMyGo 平台无法直接用。
- **判定**：京东生态内言犀胜；非京东自建平台，买小购的“票据 + 确认 + 审计”更贴合。

### 场景 C：售后政策 / 情绪安抚

- **言犀**：知识库 + 质检 + 坐席辅助 + 人机协作，适合大规模客服团队；情绪识别和转人工是产品化能力。
- **买小购**：政策智能体（MySQL 章节原文 + Milvus 语义召回）、话术库、敏感主题拒答、输入护栏；没有坐席工作台和质检。
- **判定**：言犀赢在“客服运营全流程”；买小购只覆盖“Agent 侧回答”，需要补人机协作才能打完整场景。

## 8. 定位与竞争策略

### 8.1 定位语句

> 买小购是**自建电商平台的客服智能体中枢**：把产品手册、订单、售后政策接进一个可私有化、可审计的 Agent，让“查得到、答得准、办得对”发生在平台自己的交易链路里。

### 8.2 三个战场

1. **深度场景 vs 广度覆盖**
   - 不打“全渠道客服”，打“产品手册深问答 + 订单工具 + 政策/话术”的组合拳；
   - 典型客户：有大量产品说明书/手册、客服被重复问题拖住、又不想把订单数据交给第三方的平台。
2. **数据主权 vs SaaS 便利**
   - 卖“数据不出域 + 代码可控 + 可按平台改造”；
   - 不卖“开箱即用”，卖“实施后长成你的样子”。
3. **成本/定制 vs 企业 license**
   - 对预算敏感、有技术团队的中型平台，买小购的总拥有成本更低；
   - 对没有技术团队、要全渠道的大品牌，承认言犀更合适，不硬打。

### 8.3 不打什么

- 不做电话外呼、数字人、智能质检、坐席培训、全渠道 IM 聚合；
- 不承诺“替代人工客服”，只承诺“把重复问题和高频交易动作接住”；
- 不与言犀比“1000+ 场景/十万客户”，比“你的平台里，这三类问题能不能闭环”。

### 8.4 销售话术（面对“为什么不用言犀”）

1. “您的订单/售后数据在京东吗？如果不在，言犀的深度会打折；我们的工具是直接接您自己的交易链路。”
2. “您需要数据不出域/代码级改检索和表单吗？言犀是配置级，我们可以改到切片和工具参数。”
3. “您能接受企业级 license + 实施周期吗？如果只想先跑通产品问答和订单查询，我们的起步成本低得多。”
4. “您需要 AI 直接退款/下单吗？我们不让模型直接写库，只生成草稿，用户确认后 Java 重新校验——这条审计链是我们刻意做的。”

## 9. 差距与 roadmap（建议，不是承诺）

### P0：先补“能卖”的短板（0–1 个月）

- **知识运营控制台**：上传、版本、回滚、切片预览、失败重试；当前只有脚本/接口。
- **人机协作**：转人工、坐席接管、AI 建议回复；没有它，客服主管不会放心。
- **多租户/权限**：tenant + user 隔离、管理端 RBAC；当前只有会话归属。
- **可观测**：Prometheus/OTel、检索/模型/工具耗时、错误率、成本面板。
- **评测集**：从当前回归扩到真实客服问题，建立“回答准确率/解决率/转人工率”口径。

### P1：补“能打”的差异（1–3 个月）

- **渠道适配层**：Web/APP/企微/微信客服（不做电话/数字人）；
- **知识库运营**：文档质量评分、缺口自动回流、FAQ 草稿审核发布；
- **工具市场**：把订单/退款/地址/催办做成可配置插件，但保留票据与确认；
- **私有化交付包**：离线镜像、安装脚本、备份恢复、升级回滚；
- **安全合规**：审计日志、数据脱敏、等保材料模板（不是直接拿证）。

### P2：补“能扩”的基础（3–6 个月）

- 多实例/无状态化、K8s、Redis Pub/Sub/共享状态；
- 模型路由（便宜模型做意图/贵模型做生成）、缓存与预算；
- 行业模板（3C/家电/美妆/工业品手册）；
- 开放 API/插件协议，允许客户接自己的 CRM/工单。

## 11. 风险与待验证问题

1. **公开资料偏差**：言犀的功能、价格、解决率来自第三方/官网宣传，未实测；采购前必须申请试用。
2. **生态边界**：言犀对非京东平台到底开放到什么程度？订单/售后 API 能否接自建系统？需要销售确认。
3. **私有化价格**：企业版“数十万起”是公开口径，实际按场景/算力/实施浮动。
4. **知识运营成本**：言犀和买小购都依赖知识库维护；客户是否愿意配运营人员，是成败关键。
5. **模型成本/合规**：外部模型 API 的价格、数据出境/隐私条款；私有化客户可能要求本地模型。
6. **我方规模化**：单实例、无多租户、无 K8s，当前只能做试点/POC，不能承诺大促级别 SLA。

## 12. 一页面试/答辩话术

> 京东言犀是京东云的全链路客服平台，强在京东交易生态、全渠道和企业级交付，适合中大型京东商家。买小购不和它拼广度，我们做的是自建电商平台的客服智能体：产品手册 RAG、订单工具、售后政策，全部走自己的交易链路；模型不直接写库，写操作只生成草稿，用户确认后 Java 重新校验。我们的优势是数据主权、代码级定制、成本和可审计；短板是渠道、运营工具和规模化，所以先打中型自建平台，不碰电话/数字人/全渠道。
