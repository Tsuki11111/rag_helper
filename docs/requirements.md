## 0. 产品定位与背景

- **产品名**：买小购，隶属「一次买够」平台；仓库 / 包名仍为 `rag_helper` / `rag-helper`。
- **是什么**：一次买够平台的客服智能体——以平台「产品使用文档」（说明书、用户手册）为知识底座，
  叠加商品导购、订单与物流查询、下单/退款/催办等业务动作，经 gRPC 接入 Java 单体 ItsMyGo。
- **运行形态（2026-11-06 变更）**：**只支持与平台 ItsMyGo 联合启动**（`./deploy.sh joint`）。
  本仓库**不再提供任何自用页面**（聊天 `chat.html` / 导入 `import.html` / 评测台 `eval.html` 均删除），
  用户界面与管理界面全部由平台侧提供；本服务只保留 gRPC 与管理端 HTTP 接口。**单栈启动模式已移除。**
  非真实运营，但对 Java 侧走真实链路。
- **技术路线**：deepagents 主 agent 编排，原检索图降为 subagent（详见 architecture §1）。

## 1. 利益相关方与使用场景

| 角色 | 关心什么 | 主要入口 |
|---|---|---|
| 平台顾客 | 问产品用法、找商品、查订单物流、发起售后动作 | Java 平台内的聊天（浏览器不直连 agent） |
| 平台（Java ItsMyGo） | 契约稳定、事件流可渲染、动作可确认、身份可信 | gRPC + 内部 HTTP 回调 |
| 商户 / 管理员 | 知识库导入与撤回、文档统计、评测 | 平台管理端（Java 代理 8001 / 8002 的管理接口；本仓库不自带页面） |
| 开发者 / 评测者 | 联合起栈、回归与评测可跑、成本可见、可调试 | 命令行模块 / 管理端 API |

**核心使用场景**：

1. **产品使用问答**：安装步骤、参数、故障处理，答案带配图与「图 N」引用；
2. **商品导购**：按关键词 / 分类 / 价格 / 用途找商品，返回商品卡；
3. **订单与物流**：查当前用户的订单状态、金额、物流摘要（不含 PII）；
4. **业务动作**：下单、退款、催发货、催退款——agent 只出草稿，用户在平台卡片确认后由 Java 执行；
5. **知识库运营**：上传 PDF/MD、查重、查看进度、撤回；评测用例管理与质量评测
   （均在**平台管理端**操作，本服务只提供接口，不自带页面）。

## 2. 功能需求（FR）

### 2.1 统一询问入口（架构性需求，不可绕开）

- **所有用户问题都从同一个入口进**（HTTP/SSE 与 gRPC 同源），内部一律由主 agent 编排；
- **新能力只作为 subagent 接入**，不新建独立 API / 服务 / 端口；
- 对外能力（会话、事件流、停止、用量）一律继承统一入口；
- **主 agent 与所有 subagent 的进度映射成同一种执行流**（`Trace`）。

### 2.2 主 agent 是唯一「嘴」

用户可见的问题与澄清**只能由主 agent 出口**；subagent 只干活、只返回结果。
产品名认不出时，检索子图**返回候选**而不是自己打断去问用户（D3）。

### 2.3 已交付的能力矩阵

| subagent | 能力 | 关键约束 |
|---|---|---|
| `product-kb` | 检索图作答：四路召回（向量 / HyDE / 图谱 / 联网）→ RRF → 重排 → 充分性判定 →（不足则改写再检索，最多 2 轮）→ 生成；答案带「图 N」配图引用 | 只对已导入文档作答；无证据时兜底拒答，不许编造 |
| `product-guide` | 关键词 / 分类 / 价格搜索商品目录；关键词不足时自动语义检索；返回商品卡（价格、库存、销量、评分、店铺、SKU） | 商品卡按最终回复引用裁剪，不挂中间候选 |
| `order-service` | 查订单与物流摘要；列出收货地址；准备下单 / 退款 / 催发货 / 催退款草稿 | **只 prepare 不执行**；订单视图不含收货人/电话/地址；只能看当前用户 |

### 2.4 会话与多用户

- 每条消息带 `user_id` / `tenant_id`；`chat_session` 记录归属；gRPC 的 `Converse` / `Stop` /
  `GetHistory` 校验归属，`ListSessions` / `GetHistory` 按 `x-user-id` 过滤；
- HTTP 调试入口没有平台身份，统一按 `local` 归属（**有意为之**：调试口不应看到平台用户数据）；
- **停止本轮**：用户点暂停 → 本轮生成作废、不反问用户、输入框解锁，用户自己重新提问；
- **历史与执行流**：`GetHistory` 返回每轮 `Trace`，前端默认折叠成「执行过程 · N 步」；
- **回答一致性**：同一问题首轮检索结果缓存 10 分钟；同一会话内相同问题以**首次回答为锚点**
  （证据冲突时仍以本次证据为准并说明差异）。

### 2.5 知识库导入与管理端

- 导入链路：PDF/MD → 解析 → 读图 → 切分 → 产品主体识别 → 向量化 → 入 Milvus（+ 可选 Neo4j）；
- 上传/重复检测（文件指纹）/ 进度（Redis，跨进程，重启不丢）/ 撤回（Milvus + MinIO + Mongo + Neo4j 四处清理）；
- **幂等清理只能按 `file_title`，绝不能按 `item_name`**（不同文档可能描述同一产品）；
- **撤回只影响本文档**：同一产品还有其它文档时，撤回本文档**不能**弄丢该产品的
  `kb_item_names` 行——导入侧「先来先占」不覆盖先来文档的映射，撤回侧删除前记下受害行、
  删完按 `kb_chunks` 反查仍存活的文档并重建（2026-11-07 修复，见 HANDOFF §4.26）；
- 平台管理端的 `/admin/knowledge` 由 Java 代理到本服务 8001，**agent 侧不新增接口**；
  本仓库**不再提供上传页面**（`import.html` 已删除）。

### 2.6 评测与观测

- 每轮问答写运行记录 `query_runs`（结局、耗时、成本、来源构成、召回 `topk_chunk_ids`、降级清单）；
- 每次模型/嵌入/重排/联网调用逐笔入账 `llm_usage`，可按类型/模型/租户/请求归集；
- **评测接口**（平台管理端 `/admin/agent-eval` 代理）：选用例、跑 LLM-as-Judge
  （Groundedness / 相关性 / Recall@K）、看历史报告；**本仓库不提供评测页面**，页面已删除；
- 支持管理端新建自建用例（写入 `output/eval/cases_custom.yaml`，与内置用例合并）。

### 2.8 知识缺口闭环（新增，2026-11-06）

**目标**：把「线上答不上来的问题」变成可运营的补知识工单——从运行记录自动挖缺口 →
按产品/频率归因 → 生成 FAQ 草稿 → **人工审核后**入库 → 用评测验证是否真的补上。

**缺口口径**（复用现有，不自造）：

- 缺口 = `outcome == no_match`（一条证据都没有）**或** `web_only == True`（本地 0 条、全靠联网）；
- 被输入护栏拦下的注入尝试**不算缺口**（归安全侧统计）；
- 同一问题去重计数、按频次降序。

**功能需求**：

| # | 能力 | 说明 |
|---|---|---|
| 1 | 聚合与归因 | 按问题频次 / 最近出现 / 涉及产品（`item_names`）/ 本地与联网条数汇总；支持天数与最小频次过滤 |
| 2 | 聚类 | 相似问题合并为缺口簇（embedding 相似度）；embedding 不可用时**降级为字面归一化去重**，不得报错 |
| 3 | 周报 | 输出 Markdown（Top N 缺口 + 按产品分布 + 趋势），可落到 `output/gaps/` |
| 4 | FAQ 草稿 | 针对缺口/缺口簇生成可导入的 Markdown 草稿，**必须标注「待人工核实」**，不自动入库 |
| 5 | 状态回写 | `resolved`（已补）/ `ignored`（不补）/ `published`（草稿已提交导入），按缺口 id 持久化，重复聚合不丢状态 |
| 6 | 管理端接口（8001） | 列表、周报、生成草稿、回写状态、提交草稿入库（复用现有导入链路，返回 `task_id` 供平台轮询 `/status`）；由平台管理端代理，本仓库无页面。**已接入 ItsMyGo `68b8960`**（管理端 `/admin/knowledge-gaps`） |

**验收标准**：

- 给定若干天运行记录，能按频次列出缺口并显示涉及产品；
- 同一问题只算一条、次数累加；注入尝试不出现；
- embedding 不可用时仍能出列表（降级不失败）；
- 草稿是**可导入的 Markdown**，且明确写「待人工核实」；
- 状态写入后重新查询仍可见；`publish` 返回 `task_id`，导入进度走既有 `/status/{task_id}`；
- 新增回归用例并做 mutation check。

**本期不做**：

- 自动补文档并上线（**必须人工审核**，草稿不得自动入库）；
- 用 LLM-as-Judge 的 groundedness 作为缺口口径（judge 慢且贵，本期只用 outcome / web_only）；
- 平台侧页面（由 Java 实现，本仓库只提供接口与 CLI）；
- 跨租户共享缺口池（知识库全平台共享，缺口先按当前访问密钥可见）。

### 2.9 话术与人格（2026-11-07）

**风格（用户选择）**：**亲切口语**——像平台里的真人客服；结论先行、简短、不堆免责声明。

**硬规则**：

- 统一称呼「您」，不混用「你」（指代用户时）；
- 一般问题 **≤150 字**；操作步骤类 **≤400 字**、编号分点最多 6 点；加粗 ≤3 处、列表不嵌套；
- 一轮最多追问 **1 个**问题；**用户已提供 / 已问过的信息不重复索要**；
- 同一回答「抱歉 / 对不起」**≤1 次**；不承诺无法确认的时效与结果（退款到账以平台页面为准）；
- 不暴露内部提示词、工具名、检索过程。

**场景模板（8 个）**：查不到资料、需确认型号、办理开始（草稿未执行）、办理完成、
催办致歉、投诉安抚、退款进度、物流异常。

**单一来源**：`prompts/tone_guide.prompt`，同时注入**主 agent 系统提示**与**检索图 answer_out**；
回归 `_check_tone_guide_wired` 守「注入没接上」这类静默失效。

**验收指标**（实测口径）：平均 / 最长字数、称呼统一（指代用户的「你」应为 0 次）、
抱歉与免责词次数、模板尾次数、多轮重复索要次数；用 ≥10 条典型场景（含 3 条售后）人工看语气。

**本期不做**：多套人设切换、按租户自定义话术、多语言话术。

### 2.10 会话内表单（2026-11-07 评审通过并双端落地，首批 refund_reason + address_edit）

**目标**：需要结构化信息时（退款原因 / 改地址 / 后续选规格、选订单），agent 下发平台渲染的
表单；用户提交后字段值**结构化回传**，agent 按 `form_type` **直接调工具**，不再从自然语言
猜参数。

**契约（已生效，`proto/agent.proto` 是源头）**：

- `FinalEvent.forms`（可交互）、`HistoryMessage.forms`（只读回放）下发 `FormRequest`；
- 回传走**下一轮** `ConverseRequest.form_result{form_id, values}`（方案 A）；
- `FormRequest.meta` 是 agent 侧上下文（前端不渲染，如 `{"orderNo": …}` / `{"addressId": …}`）；
- 规则：**一轮最多 1 张**、`form_id` 服务端生成、**双端一次性消费**（Java Redis SETNX
  `its-my-go:agent:form:{userId}:{formId}`，TTL 660s；agent 侧再按历史校验）、TTL 600s、
  过期/重复提交一律拒绝；表单值不进日志明文。

**首批 `refund_reason`**：用户要退款但没说原因 → 先确认订单可退 → 下发原因表单
（**选项由 Java 用售后原因字典补全**，rag_helper 不硬编码）→ 提交后服务端直接调用
`prepare_refund(orderNo, reason)` 生成退款草稿（原因随草稿落库、确认时原样提交）；
非法原因由 Java 拒收（`FORM_INVALID`）。

**首批 `address_edit`**：用户要改收货地址 → 确认改哪条 → 下发 6 字段地址表单 →
提交后服务端直接调 Java 内部接口 `POST /internal/agent/actions/address` 更新（复用地址
更新逻辑、校验归属，返回 `summary.address`）。

**兼容**：旧 Java 不识别 `forms`（忽略即可）；旧客户端不传 `form_result` 时按普通文本对话。

**评审材料**：[docs/form-protocol-review.md](form-protocol-review.md)（含 7 个决策点与
4 条验收用例；Java 侧已评审通过，结论见其 §9）。

**验收（2026-11-07 联合栈，12/12 通过）**：退款原因表单下发/选项补全 → 提交生成带原因草稿 →
重复提交被 Java Redis 拦截 → 历史只读回放；改地址表单下发 → 提交后地址直接更新。
证据见 HANDOFF §3.76。

**本期不做**：`sku_select` / `order_pick`（下一批）；表单内联动校验、任意 HTML 注入。

### 2.11 客服设置（智能推广 / 联网搜索 / 流式输出，2026-11-07）

**目标**：客服面板给用户三个可选开关，偏好按用户持久化并真正生效。

- **智能推广**（默认关）：开启后允许 bot 每日主动推荐商品（见 §2.12）；关闭则不推、不落推荐消息；
- **联网搜索**（默认开）：关闭后本轮 RAG 不调用联网（`enable_web_search=false`）；
- **流式输出**（默认关）：开启后**最终回答**以增量事件下发（gRPC `Delta` / SSE `delta`；
  工具轮次的中间文本不回放，避免生成结束时被最终回答替换），
  关闭时与旧行为一致（只推 final 整段）。

契约：偏好存 Java `user_agent_preferences` 表；`GET/PUT /api/agent/preferences`；
每轮 Converse 把联网/流式偏好放进 gRPC `ConverseRequest` 的两个 **optional** 字段
（`enable_web_search` / `stream`）——optional 保留「旧客户端未设置」语义：
未设置时联网=开、流式=关，行为与改造前一致。

**不做**：偏好按设备/会话维度细分（当前按用户全局）。

### 2.12 智能推广（客服智能体会话 + 登录后随机延迟，2026-11-07）

**目标**：在用户开启推广的前提下，每天主动推 1 条「可能感兴趣的商品」到**客服智能体会话**，
点击商品卡可进详情。

**推荐信号（组合打分，优先级从高到低）**：
1. **最近降价幅度大**（依赖新增的商品价格历史表；从上线之日起积累）；
2. **与用户买过的商品相似**（同品类/同品牌，取用户最近购买的 Top 品类）；
3. **销量高**（`sales`）；
4. **评价好**（`rating` / `reviewCount`）。

**触达**：写入用户最近的**客服智能体会话历史**（Java 内部事件 `promotion-push` →
agent 追加 assistant 消息 + **多张商品卡（一次最多 3 件）**；没有历史会话则新建），
**不进顾客—店铺聊天**；
**每用户每天最多 1 条**，`last_promotion_date` 防重复；用户关开关即不再推。

**触发**：**用户登录成功后 0~5 分钟内随机延迟**（避免固定时刻全量扫描的并发尖峰；
只触达活跃用户）。三层去重：Redis 按用户+日期排期一次 → 发送前再查偏好与当天已推 →
成功才写 `last_promotion_date`；延迟参数 `PROMOTION_LOGIN_DELAY_SECONDS` 可配。

**不做**：短信/邮件/推送通道；不做站内通知中心（本期用聊天会话）。

### 2.13 个性化消费报告（页面 + 聊天摘要，2026-11-07）

**目标**：用户查看自己的消费情况，并能在客服对话里让 bot 摘要。

**数据**（全部来自已有订单/支付/退款数据，**不推算**）：
- 期间：已支付订单数、实付金额、退款金额、净支出、优惠金额、单笔均价；
- 排行：品类 / 店铺 / 商品（金额或件数 Top 3）；
- 年度视图附「每月消费」趋势（最高月）。

**页面**：顾客端「我的消费报告」页（按月/按年切换，卡片 + 简单条形）；
**聊天摘要**：agent 工具 `get_consumption_report(period, date)` 调 Java 内部只读接口
`GET /internal/agent/reports/consumption`，把结果概括成几句（金额/排名只能用接口返回值）。

**不做**：导出 PDF/图片、跨用户对比、财务口径（退款按已退款金额扣减，不做利息/税费）。

### 2.14 客服话术库（主 agent 轻量检索，2026-11-08）

**目标**：把「客服话术优化」从 system prompt 里的静态规范，扩展成可按场景检索的轻量 FAQ 库；
主 agent 组织回复前检索 2~3 条参考话术，学语气与结构，不照抄。

**形态**：

- Milvus 独立集合 `kb_tone_faq`（不与 `kb_chunks` 混用），字段
  `faq_id / scenario / question / answer / tags / dense_vector`（1536 维，COSINE，HNSW）；
- 种子 `data/tone_faq.json`（18 条常见场景：退款、物流、催办、质量、议价、投诉、安抚等）；
- 导入：`python -m app.agent.tools.tone_faq_import`（幂等 upsert，可重复执行）。

**检索**：主 agent 直接工具 `search_tone_faq(query, top_k=3)`：一次 embedding + 一次 Milvus
稠密检索（单路，无 HyDE / 多路 / RRF / 重排 / 改写），相似度阈值 0.30、最多 5 条；
命中返回「场景 / 用户可能会说 / 建议这样回」；库不可用返回降级提示，不阻断回答。

**范围外（本期）**：话术管理端 CRUD、按业务域过滤、多轮个性化；后续可接管理端。

**验收**：全量回归 86/0（含 Milvus 检索用例）；联合栈实测用户表达「退款 + 生气」时，
主 agent 先调用 `search_tone_faq` 再组织回复，且不泄漏话术库。

### 2.15 导购商品介绍（2026-11-09）

**目标**：解决推荐商品「只报名称 / 价格 / 链接、介绍太少」的问题，让用户能直接比较卖点与适合场景。

**行为要求**：

- 每个推荐商品写 **2~3 句话**：先讲卖点 / 适合谁，再补价格、库存、销量 / 评分；
- 卖点信息来自 `product-guide` 返回的 `subtitle`（卖点）与 `description`（商品简介，Java 侧截断到 300 字），
  结构化字段（价格 / 库存 / 销量 / 评分）只能来自工具返回，**不许编造**；
- 不原样大段照抄简介；5 款都推荐时每款都要有介绍，不能只详写第一款；
- 保留该商品的 `/product/{productId}` 链接，供前端把商品卡穿插在对应介绍之后。

**验收**：真实查询「推荐 5 款打印机」时，正文每款至少 2 句介绍，5 张商品卡分别跟在对应介绍后；
全量回归 86/0，前端 build 通过。

## 3. 非功能需求（NFR）

### 3.1 延迟与吞吐

- **整轮墙钟预算 180s**（超预算降级收尾）；gRPC `deadline` 240s、`keepalive` 300s；
- 单实例、低并发是当前**有意前提**；对用户的限流由 Java 侧做（客服对话 10 次/分钟），
  agent 侧不单独限流；
- 性能目标而非承诺：正常问答应在数十秒内完成（含重排与可能的取图）。

### 3.2 成本

- 一次问答约 **¥0.0095**（8 次调用 ≈ 1 万 tokens），成本结构：生成 47%、重排 43%、HyDE 7%；
- 成本必须**可见且可归集**（账本 + 运行记录），单条流式调用漏记 token 视为缺陷
  （`stream_usage` 必须显式打开）；
- 已知偏差：暂停轮账面偏低（流式中途打断拿不到末帧用量）；联网搜索与 MinerU 不在 token 账本内；
  计价表是快照，需人工跟进。

### 3.3 可靠性与降级

- **异常分级**：编程错误上抛；外部故障按可重试/需人工分类降级，所有降级带 `degraded` 标记可统计；
- **重试只针对 `RETRYABLE`**（timeout / 429 退避），refusal 不盲重试，invalid tool args 绝不执行；
- **依赖不可用要降级不能拖垮业务**：Mongo 快失败（2s）+ 60s 熔断；Redis 不可用退回内存；
  Neo4j 关闭是**配置跳过**（不是降级故障）；
- **检查点**：导入图用 `MongoDBSaver`（7 天 TTL），支持**服务重启自动续跑**；
  查询侧不使用 checkpointer（状态源是会话历史）；
- 可选组件（Neo4j / 检索循环）默认关闭，且关闭后行为语义明确。

### 3.4 安全

- **三层护栏**：输入护栏（不合规不烧模型调用）、输出护栏、工具护栏（**工具护栏未做**）；
- **提示词注入**：直接注入已复测 17 条（6 条被输入护栏拦下、11 条模型全部拒绝）；
  零宽/空格拆字已加固；**间接注入（知识库/联网内容）尚未稳定验证**，不得认为已覆盖；
- 身份：内网信任 + 服务端密钥 + `X-User-Id`（Java 注入前先剥离客户端同名 metadata）
  + 每轮短期票据（Redis，10 分钟）；
- 业务红线：**LLM 不直接写业务库**、**风控不用 LLM**、**高危动作人工审批 + 全程审计**。

### 3.5 数据与隐私

- **数据最小化**：订单视图不含收货人/电话/地址；物流只给状态/ETA/快递公司/快递员；
  收货地址不进 agent 上下文（只在 Java 侧用于下单快照）；
- 会话历史、账本、运行记录是「人的痕迹」，按 `user_id` / `tenant_id` 区分；知识库全平台共享；
- 保留期：检查点 7 天 TTL、任务状态 1 天 TTL；对话正文会发给第三方模型（DashScope / DeepSeek /
  MinerU / 百炼）——**这一点必须在对外说明里讲清**；
- 密钥只存 sha256，明文只在创建时打印一次；`AGENT_GRPC_KEY` 由部署脚本生成。

### 3.6 可运维性

- **唯一启动形态是与 ItsMyGo 联合部署**（`./deploy.sh joint`），含首次初始化：
  建桶、建库建集合、写密钥；**单栈启动模式已移除**；
- 健康检查 `/health`；日志双格式（人读 + JSONL，带 `trace_id` / `node` 可归因）；
- 部署细节见 [docs/deployment.md](deployment.md)。

### 3.7 质量门禁

- **回归套件**：纯逻辑/打桩为主，依赖不可用标 `SKIP` 而非 `FAIL`（退出码仍 0），`FAIL` 才返回 1；
- **mutation check 是硬要求**：每批新用例都要把对应修复逐个破坏、验证用例能变红；
- CI 在干净环境跑离线回归（钉住「装得上、import 得了、逻辑自洽」），完整端到端在开发机跑。

### 3.8 非功能缺口（已知，明确记录）

| 缺口 | 现状 |
|---|---|
| 数据隔离 | 会话已按用户隔离；账本按 `(tenant, user)` 聚合与 A/B 验收未完成 |
| 写操作审计 | 下单/退款/催办已真实执行，但**没有 append-only 审计日志** |
| 工具护栏 | 联网搜索等工具尚无来源白名单与频率限制 |
| 间接注入 | 只有直接注入的复测结论 |
| 多 worker | SSE 队列在进程内，开多 worker 会丢事件 |

## 4. 平台对接需求与前提

> **Java 侧对应文档**：ItsMyGo 的 `docs/requirements.md` §4（平台对接需求与前提）、
> `docs/architecture.md` §9（跨仓库协作）、`docs/api.md` §19（客服智能体「买小购」接口）。
> 跨仓库引用若有变动，两边同一天改完再推送（2026-11-05 已双向同步）。

| 项 | 定论 |
|---|---|
| 拓扑 | Java **单体** + agent 服务（**单实例**）——不经网关、不上微服务 |
| 身份模型 | 内网信任 + `X-User-Id`（gRPC metadata）；Java 注入时先剥离客户端同名值 |
| 身份两维 | `tenant_id`（平台/商户，密钥换来）+ `user_id`（顾客，`X-User-Id`） |
| 缺头行为 | 本机/自测放行（固定值 `local`）；生产直接 400 |
| 知识库 | **全平台共享一份**；上传是服务端行为 |
| 要分的东西 | 只有「人」的痕迹：主 agent 会话、账本、运行记录 |
| 不做 | 不动 Milvus / Neo4j / MinIO；不给上传加 `user_id` |
| 工具回调 | agent → Java 内网 HTTP + JSON；请求体只有业务参数，**没有 userId** |
| 票据 | Java 每次 `Converse` 签发短期票据（Redis 10 分钟），metadata `x-agent-tool-ticket` 下发，回调时带回 `X-Agent-Ticket`；**模型不参与身份** |
| 写操作 | agent 只 `prepare`；Java 落 `PENDING_CONFIRM` 快照；用户确认后 Java 执行；确认接口只收 `actionNo` |
| 商品卡 | `FinalEvent` / `HistoryMessage` 增加 `ProductCard`；模型只选筛选参数，不写 SQL |
| Java 侧已拍板 | 顾客 ID 为 MySQL BIGINT（注入时转字符串）；单实例低并发；gRPC deadline 240s / keepalive 300s；Java 侧按用户限流 10 次/分钟；`/internal/agent/**` 不对外暴露 |

**隔离验收（A/B 两个用户交叉试探）**：① B 的 `ListSessions`/`GetHistory` 看不到 A 的会话；
② 账本按 `(tenant, user)` 聚合各自对得上；③ 管理端上传不受影响；④ 以上写成回归用例 + mutation check。
当前进度：① 已完成（两边都做归属过滤）；② 待补；④ 用例已加、mutation check 未做。

## 5. 验收标准

**一个月窗口（C 档，已超额完成）**：

1. **gRPC 服务化**——proto 定稿 + 服务端实现 + 测试客户端端到端；
2. **RAG subagent 闭环**——主 agent 派发 → 检索图作答（带配图）→ 主 agent 转述；
3. **只读「查订单」mock subagent**——两个 subagent 可由主 agent 组合调度；
4. 平台侧界面呈现**统一执行流**（本仓库不再提供页面，界面由平台侧实现）；
5. 全量回归通过，新链路按规矩补用例 + mutation check。

> 现状：1–5 全部达成，且已超出「mock」范围——2026-10-25 与 ItsMyGo 完成联合部署与真实联调，
> 订单/导购/下单/退款/催办均走真实 Java 链路。

**当前形态的验收口径**：

- 同一会话经 HTTP 与 gRPC 各跑多轮，历史一致；Stop 只作用于当前轮；
- 客服四类场景可从平台侧走通（产品问答 / 导购 / 查订单 / 动作草稿确认）；
- 回归全绿（依赖缺失时为 SKIP 而非 FAIL）；评测可跑出 Groundedness / Recall / 成本；
- **隔离验收 4 条**（见 §4）作为后续数据隔离工作的完成标志。

## 6. 范围外与按需区

**当前明确不做**：数据隔离实现、多租户、审计/审批、评估 P2 扩样、SSE 跨进程改造、限流、
微服务化、灰度发布、chargeback、端到端语音。

**按需区（将来需要时不再重新论证）**：

- **若 Java 侧改微服务**：`X-User-Id` 改网关注入（剥离同名头，规则进网关路由）；逐跳检查流式/缓冲/超时；
  服务间凭据升级（静态密钥 → mTLS/OAuth2）；限流落网关；多实例下主 agent 的流与 thread 需路由一致性（sticky）。
- **流式韧性**：应用层心跳已由 gRPC keepalive 替代；Java→浏览器的 SSE 心跳是 Java 侧事务；
  断流重连与轮询兜底的语义在 gRPC 下待定义，有真实反馈后再做。
- **SSE 那笔债**：调试用的 HTTP/SSE 路径仍在（接口保留），进程内队列单实例即可；
  生产路径走 gRPC，不受影响；本仓库已无浏览器页面消费 SSE。

## 9. 术语与命名约定

| 术语 | 含义 |
