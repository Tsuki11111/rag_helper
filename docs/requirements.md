## 0. 产品定位与背景

- **产品名**：买小购，隶属「一次买够」平台；仓库 / 包名仍为 `rag_helper` / `rag-helper`。
- **是什么**：一次买够平台的客服智能体——以平台「产品使用文档」（说明书、用户手册）为知识底座，
  叠加商品导购、订单与物流查询、下单/退款/催办等业务动作，经 gRPC 接入 Java 单体 ItsMyGo。
- **定位**：自用与学习练手，全本地 Docker 运行；**非真实运营**，但对 Java 侧走真实链路。
- **技术路线**：deepagents 主 agent 编排，原检索图降为 subagent（详见 architecture §1）。

## 1. 利益相关方与使用场景

| 角色 | 关心什么 | 主要入口 |
|---|---|---|
| 平台顾客 | 问产品用法、找商品、查订单物流、发起售后动作 | Java 平台内的聊天（浏览器不直连 agent） |
| 平台（Java ItsMyGo） | 契约稳定、事件流可渲染、动作可确认、身份可信 | gRPC + 内部 HTTP 回调 |
| 商户 / 管理员 | 知识库导入与撤回、文档统计、评测 | 管理端 HTTP（8001）+ 评测台（8002 `/eval.html`） |
| 开发者 / 评测者 | 一键起栈、回归与评测可跑、成本可见、可调试 | 本地脚本 / 页面 / 命令行模块 |

**核心使用场景**：

1. **产品使用问答**：安装步骤、参数、故障处理，答案带配图与「图 N」引用；
2. **商品导购**：按关键词 / 分类 / 价格 / 用途找商品，返回商品卡；
3. **订单与物流**：查当前用户的订单状态、金额、物流摘要（不含 PII）；
4. **业务动作**：下单、退款、催发货、催退款——agent 只出草稿，用户在平台卡片确认后由 Java 执行；
5. **知识库运营**：上传 PDF/MD、查重、查看进度、撤回；评测用例管理与质量评测。

## 2. 功能需求（FR）

### 2.1 统一询问入口（架构性需求，不可绕开）

- **所有用户问题都从同一个入口进**（HTTP/SSE 与 gRPC 同源），内部一律由主 agent 编排；
- **新能力只作为 subagent 接入**，不新建独立 API / 服务 / 端口；
- 对外能力（会话、事件流、停止、用量）一律继承统一入口；
- **主 agent 与所有 subagent 的进度映射成同一种执行流**（`Trace`）。

### 2.2 主 agent 是唯一「嘴」

用户可见的问题与澄清**只能由主 agent 出口**；subagent 只干活、只返回结果。
产品名认不出时，检索子图**返回候选**而不是自己打断去问用户（D3）。

### 2.3 已交付的能力矩阵

| subagent | 能力 | 关键约束 |
|---|---|---|
| `product-kb` | 检索图作答：四路召回（向量 / HyDE / 图谱 / 联网）→ RRF → 重排 → 充分性判定 →（不足则改写再检索，最多 2 轮）→ 生成；答案带「图 N」配图引用 | 只对已导入文档作答；无证据时兜底拒答，不许编造 |
| `product-guide` | 关键词 / 分类 / 价格搜索商品目录；关键词不足时自动语义检索；返回商品卡（价格、库存、销量、评分、店铺、SKU） | 商品卡按最终回复引用裁剪，不挂中间候选 |
| `order-service` | 查订单与物流摘要；列出收货地址；准备下单 / 退款 / 催发货 / 催退款草稿 | **只 prepare 不执行**；订单视图不含收货人/电话/地址；只能看当前用户 |

### 2.4 会话与多用户

- 每条消息带 `user_id` / `tenant_id`；`chat_session` 记录归属；gRPC 的 `Converse` / `Stop` /
  `GetHistory` 校验归属，`ListSessions` / `GetHistory` 按 `x-user-id` 过滤；
- HTTP 调试入口没有平台身份，统一按 `local` 归属（**有意为之**：调试口不应看到平台用户数据）；
- **停止本轮**：用户点暂停 → 本轮生成作废、不反问用户、输入框解锁，用户自己重新提问；
- **历史与执行流**：`GetHistory` 返回每轮 `Trace`，前端默认折叠成「执行过程 · N 步」；
- **回答一致性**：同一问题首轮检索结果缓存 10 分钟；同一会话内相同问题以**首次回答为锚点**
  （证据冲突时仍以本次证据为准并说明差异）。

### 2.5 知识库导入与管理端

- 导入链路：PDF/MD → 解析 → 读图 → 切分 → 产品主体识别 → 向量化 → 入 Milvus（+ 可选 Neo4j）；
- 上传/重复检测（文件指纹）/ 进度（Redis，跨进程，重启不丢）/ 撤回（Milvus + MinIO + Mongo + Neo4j 四处清理）；
- **幂等清理只能按 `file_title`，绝不能按 `item_name`**（不同文档可能描述同一产品）；
- 平台管理端的 `/admin/knowledge` 由 Java 代理到本服务 8001，**agent 侧不新增接口**。

### 2.6 评测与观测

- 每轮问答写运行记录 `query_runs`（结局、耗时、成本、来源构成、召回 `topk_chunk_ids`、降级清单）；
- 每次模型/嵌入/重排/联网调用逐笔入账 `llm_usage`，可按类型/模型/租户/请求归集；
- 评测台：选用例、跑 LLM-as-Judge（Groundedness / 相关性 / Recall@K）、看历史报告；
- 支持管理端新建自建用例（写入 `output/eval/cases_custom.yaml`，与内置用例合并）。

## 3. 非功能需求（NFR）

### 3.1 延迟与吞吐

- **整轮墙钟预算 180s**（超预算降级收尾）；gRPC `deadline` 240s、`keepalive` 300s；
- 单实例、低并发是当前**有意前提**；对用户的限流由 Java 侧做（客服对话 10 次/分钟），
  agent 侧不单独限流；
- 性能目标而非承诺：正常问答应在数十秒内完成（含重排与可能的取图）。

### 3.2 成本

- 一次问答约 **¥0.0095**（8 次调用 ≈ 1 万 tokens），成本结构：生成 47%、重排 43%、HyDE 7%；
- 成本必须**可见且可归集**（账本 + 运行记录），单条流式调用漏记 token 视为缺陷
  （`stream_usage` 必须显式打开）；
- 已知偏差：暂停轮账面偏低（流式中途打断拿不到末帧用量）；联网搜索与 MinerU 不在 token 账本内；
  计价表是快照，需人工跟进。

### 3.3 可靠性与降级

- **异常分级**：编程错误上抛；外部故障按可重试/需人工分类降级，所有降级带 `degraded` 标记可统计；
- **重试只针对 `RETRYABLE`**（timeout / 429 退避），refusal 不盲重试，invalid tool args 绝不执行；
- **依赖不可用要降级不能拖垮业务**：Mongo 快失败（2s）+ 60s 熔断；Redis 不可用退回内存；
  Neo4j 关闭是**配置跳过**（不是降级故障）；
- **检查点**：导入图用 `MongoDBSaver`（7 天 TTL），支持**服务重启自动续跑**；
  查询侧不使用 checkpointer（状态源是会话历史）；
- 可选组件（Neo4j / 检索循环）默认关闭，且关闭后行为语义明确。

### 3.4 安全

- **三层护栏**：输入护栏（不合规不烧模型调用）、输出护栏、工具护栏（**工具护栏未做**）；
- **提示词注入**：直接注入已复测 17 条（6 条被输入护栏拦下、11 条模型全部拒绝）；
  零宽/空格拆字已加固；**间接注入（知识库/联网内容）尚未稳定验证**，不得认为已覆盖；
- 身份：内网信任 + 服务端密钥 + `X-User-Id`（Java 注入前先剥离客户端同名 metadata）
  + 每轮短期票据（Redis，10 分钟）；
- 业务红线：**LLM 不直接写业务库**、**风控不用 LLM**、**高危动作人工审批 + 全程审计**。

### 3.5 数据与隐私

- **数据最小化**：订单视图不含收货人/电话/地址；物流只给状态/ETA/快递公司/快递员；
  收货地址不进 agent 上下文（只在 Java 侧用于下单快照）；
- 会话历史、账本、运行记录是「人的痕迹」，按 `user_id` / `tenant_id` 区分；知识库全平台共享；
- 保留期：检查点 7 天 TTL、任务状态 1 天 TTL；对话正文会发给第三方模型（DashScope / DeepSeek /
  MinerU / 百炼）——**这一点必须在对外说明里讲清**；
- 密钥只存 sha256，明文只在创建时打印一次；`AGENT_GRPC_KEY` 由部署脚本生成。

### 3.6 可运维性

- 一键 Compose 起全栈（含首次初始化：建桶、建库建集合、写密钥）；`deploy.sh joint` 与 ItsMyGo 联合启动；
- 健康检查 `/health`；日志双格式（人读 + JSONL，带 `trace_id` / `node` 可归因）；
- 部署细节见 [docs/deployment.md](deployment.md)。

### 3.7 质量门禁

- **回归套件**：纯逻辑/打桩为主，依赖不可用标 `SKIP` 而非 `FAIL`（退出码仍 0），`FAIL` 才返回 1；
- **mutation check 是硬要求**：每批新用例都要把对应修复逐个破坏、验证用例能变红；
- CI 在干净环境跑离线回归（钉住「装得上、import 得了、逻辑自洽」），完整端到端在开发机跑。

### 3.8 非功能缺口（已知，明确记录）

| 缺口 | 现状 |
|---|---|
| 数据隔离 | 会话已按用户隔离；账本按 `(tenant, user)` 聚合与 A/B 验收未完成 |
| 写操作审计 | 下单/退款/催办已真实执行，但**没有 append-only 审计日志** |
| 工具护栏 | 联网搜索等工具尚无来源白名单与频率限制 |
| 间接注入 | 只有直接注入的复测结论 |
| 多 worker | SSE 队列在进程内，开多 worker 会丢事件 |

## 4. 平台对接需求与前提

> **Java 侧对应文档**：ItsMyGo 的 `docs/requirements.md` §4（平台对接需求与前提）、
> `docs/architecture.md` §9（跨仓库协作）、`docs/api.md` §19（客服智能体「买小购」接口）。
> 跨仓库引用若有变动，两边同一天改完再推送（2026-11-05 已双向同步）。

| 项 | 定论 |
|---|---|
| 拓扑 | Java **单体** + agent 服务（**单实例**）——不经网关、不上微服务 |
| 身份模型 | 内网信任 + `X-User-Id`（gRPC metadata）；Java 注入时先剥离客户端同名值 |
| 身份两维 | `tenant_id`（平台/商户，密钥换来）+ `user_id`（顾客，`X-User-Id`） |
| 缺头行为 | 本机/自测放行（固定值 `local`）；生产直接 400 |
| 知识库 | **全平台共享一份**；上传是服务端行为 |
| 要分的东西 | 只有「人」的痕迹：主 agent 会话、账本、运行记录 |
| 不做 | 不动 Milvus / Neo4j / MinIO；不给上传加 `user_id` |
| 工具回调 | agent → Java 内网 HTTP + JSON；请求体只有业务参数，**没有 userId** |
| 票据 | Java 每次 `Converse` 签发短期票据（Redis 10 分钟），metadata `x-agent-tool-ticket` 下发，回调时带回 `X-Agent-Ticket`；**模型不参与身份** |
| 写操作 | agent 只 `prepare`；Java 落 `PENDING_CONFIRM` 快照；用户确认后 Java 执行；确认接口只收 `actionNo` |
| 商品卡 | `FinalEvent` / `HistoryMessage` 增加 `ProductCard`；模型只选筛选参数，不写 SQL |
| Java 侧已拍板 | 顾客 ID 为 MySQL BIGINT（注入时转字符串）；单实例低并发；gRPC deadline 240s / keepalive 300s；Java 侧按用户限流 10 次/分钟；`/internal/agent/**` 不对外暴露 |

**隔离验收（A/B 两个用户交叉试探）**：① B 的 `ListSessions`/`GetHistory` 看不到 A 的会话；
② 账本按 `(tenant, user)` 聚合各自对得上；③ 管理端上传不受影响；④ 以上写成回归用例 + mutation check。
当前进度：① 已完成（两边都做归属过滤）；② 待补；④ 用例已加、mutation check 未做。

## 5. 验收标准

**一个月窗口（C 档，已超额完成）**：

1. **gRPC 服务化**——proto 定稿 + 服务端实现 + 测试客户端端到端；
2. **RAG subagent 闭环**——主 agent 派发 → 检索图作答（带配图）→ 主 agent 转述；
3. **只读「查订单」mock subagent**——两个 subagent 可由主 agent 组合调度；
4. 自用界面呈现**统一执行流**；
5. 全量回归通过，新链路按规矩补用例 + mutation check。

> 现状：1–5 全部达成，且已超出「mock」范围——2026-10-25 与 ItsMyGo 完成联合部署与真实联调，
> 订单/导购/下单/退款/催办均走真实 Java 链路。

**当前形态的验收口径**：

- 同一会话经 HTTP 与 gRPC 各跑多轮，历史一致；Stop 只作用于当前轮；
- 客服四类场景可从平台侧走通（产品问答 / 导购 / 查订单 / 动作草稿确认）；
- 回归全绿（依赖缺失时为 SKIP 而非 FAIL）；评测可跑出 Groundedness / Recall / 成本；
- **隔离验收 4 条**（见 §4）作为后续数据隔离工作的完成标志。

## 6. 范围外与按需区

**当前明确不做**：数据隔离实现、多租户、审计/审批、评估 P2 扩样、SSE 跨进程改造、限流、
微服务化、灰度发布、chargeback、端到端语音。

**按需区（将来需要时不再重新论证）**：

- **若 Java 侧改微服务**：`X-User-Id` 改网关注入（剥离同名头，规则进网关路由）；逐跳检查流式/缓冲/超时；
  服务间凭据升级（静态密钥 → mTLS/OAuth2）；限流落网关；多实例下主 agent 的流与 thread 需路由一致性（sticky）。
- **流式韧性**：应用层心跳已由 gRPC keepalive 替代；Java→浏览器的 SSE 心跳是 Java 侧事务；
  断流重连与轮询兜底的语义在 gRPC 下待定义，有真实反馈后再做。
- **SSE 那笔债**：自用路径仍用 SSE + 进程内队列——**单实例即可**；生产路径走 gRPC，不受影响。

2. **多租户排期**：会话已隔离，但账本/运行记录/成本归因与完整 A/B 验收未排期；
3. **供应商与计价维护**：模型供应商价格表是快照，需人工跟；`qwen3-vl-plus` 视觉模型未入计价表；
4. **商品规模上限**：语义索引在内存（TTL 300s），商品量大后需迁 Milvus——触发条件待定。

（原阶段的三个待定问题——Java 侧状态、主 agent tool calling 模型、proto 与订单契约——均已落地，
见 [docs/architecture.md](architecture.md) §6。）

## 9. 术语与命名约定

| 术语 | 含义 |
|---|---|
| 产品 / 商品 | **产品** = 文档描述的产品主体（`item_name`）；**商品** = 平台商品目录里的条目（ProductCard） |
| `item_name` | 产品主体标识；变量名与集合名（`ITEM_NAME_COLLECTION`）保持不变 |
| subagent | 主 agent 下的三个子智能体：`product-kb` / `product-guide` / `order-service` |
| `session_id` / `run_id` / `trace_id` | 会话 / 一轮问答 / 一次可归因调用链；`run_id` 同时是暂停令牌与检查点 thread |
| `outcome` | 一轮问答的六档结局（含 `waiting_user` 等），用于运行记录与报表 |
| M / P / E 编号 | `M0–M13` 里程碑；`P0–P5` 评估阶段；`E1–E6` 评估环节 |
| prepare / 草稿 | 业务动作的「提议」形态：**尚未执行**，需用户确认 |
