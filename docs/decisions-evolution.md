## D1 目标形态：deepagents 主 agent + RAG 降为 subagent

**结论**：项目从「单一 RAG 服务」进化为**网购平台智能客服 agent**——
用 LangChain `deepagents` 建主 agent，现有检索图封装为 `CompiledSubAgent`；
后续持续新增业务 subagent；经 **gRPC** 接入 Java 网购平台。

**理由**：deepagents 的 subagent 机制（同步调用、上下文隔离、只回最终结果）
与「RAG 作为一种能力被编排」的定位天然吻合；框架与现有
langchain 1.x / langgraph 1.x 栈同源，检索图、检查点、记账、护栏全部可复用。

## D3 RAG 无状态化：中断收归上层、历史归主 agent

**结论**：图内**不再 `interrupt()`**——认不出产品时返回候选，由主 agent 用对话问用户；
RAG 的 `chat_message` 会话历史停用（或仅存档），对话状态由主 agent 独有。

**理由**：deepagents 的 subagent 是「隔离上下文、只回最终结果」的一次性调用，
子 agent 中途冒出提问与模型别扭；客服场景里主 agent 自己也要问用户，
两张嘴会打架。「永远只有一份对话状态」是 `java-integration.md` §13.3 就立过的红线，
本决策是它的落地。

**与旧论证的关系（重要）**：§13.3 曾论证「RAG 当**工具**、别当子 agent」，
理由是「两份会话状态打架」。deepagents 的 subagent 恰好就是「工具形态的 agent 图」
（同步、无状态、单次返回），加上历史归主 agent 后**只有一份状态**——
本决策与旧论证不冲突，是同一结论在新框架下的实现。

**代价**：查询侧图内 HITL（interrupt / resume / 确认卡片）从主链路退役；
导入侧的检查点用途（重启续跑）不受影响。

## D5 企业化与评估两条路线收编、随新形态重置

**结论**：两条旧路线（当初按「RAG 是主 agent」设计）不再独立演进，
**重置后排入进化路线总纲**：评估对象从「检索质量」扩展为
「主 agent 编排质量 + subagent 质量」；观测/记账覆盖 agent 调度层；
治理（审计/审批）在客服场景从加分项变刚需；数据隔离对象从「RAG 会话」
改为「主 agent 会话 + 账本 + 运行记录」。

**理由**：RAG 降级为 subagent 后，两条路线的评估与观测对象都变了；
继续按旧对象排期会为不存在的主体重投资（本项目已有一次
「按 java 场景重估 Phase 3」的先例，同一逻辑延续）。

## D8 检索子图加有界自纠正循环，而不是在主 agent 层再套一层（2026-10-20）

**结论**：agent loop 放在检索子图内部（`node_rerank` 之后）：判充分性 → 不足则**受约束地**
改写检索词再检索一轮（最多 2 轮）→ 耗尽回落第一轮证据。判定器只在红灯轮次调用，
默认关闭（`RETRIEVAL_MAX_ROUNDS=1`），实测后再开启。

**理由**：主 agent 已经是 deepagents 的 model↔tools 循环，再套一层会与事件流、预算、暂停、
运行记录四套机制打架；检索子图是固定 DAG，是唯一真正缺循环、且最值得自纠正的地方。
**对抗目标漂移的核心不是「循环次数」，而是「意图锚 + 验证」**：作答与重排始终用
`rewritten_query`（用户意图），循环改写只动 `retrieval_query`（检索探针）；
判定永远对 `original_query`；改写必须保留产品名；失败回落第一轮证据。
没有这四条，越多的循环只会把偏差越滚越大。

**代价**：失败轮次的尾延迟与成本上升（有轮次 / 预算 / 守卫三重上限兜住）；
判定器是运行时组件，不是评估指标 —— P3 的 LLM-as-Judge 是另一件事，别混用概念。
